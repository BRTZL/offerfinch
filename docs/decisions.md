# Decisions

What was decided and why, in order. `PLAN.md` holds the current plan; this file holds the reasoning.

## Product (2026-10-30)

| Decision | Why |
|---|---|
| Find jobs, prepare applications, apply only after approval of each one | The user wants to see the posting, CV and letter before anything is sent |
| Every claim traces to the profile | Avoids sending invented experience at volume |
| ~~Hard filter before any tailoring~~ Replaced (2026-11-05, user's choice): no rule rejects a job: every job a search finds goes to the fit score, which caps a must-have work right, place, citizenship, clearance or language the user does not meet below their minimum, so it ends as a low score with the blocker as its reason (see "2026-11-05: No hard filter; the fit score decides") | Northbeam and Assertive Yield both had location or language requirements the user may not meet; tailoring those wastes money |
| Scope is all phases, ending in a product the user runs | User: complete everything so it works end to end |
| SaaS later, every record has `user_id` now | Avoids a rewrite; billing skipped while it's internal |

## Filter settings

- Right to work in Turkey only; sponsorship needed elsewhere.
- Keep remote from Turkey or global remote, plus hybrid or on-site in Turkey.
- Relocation roles are off by default, editable in settings.
- No daily limit on applications; only approvals limit them.
- Watchlist is discovered from job boards, seeded from the shortlist; the user can remove any company.

## Stack

Better-T-Stack scaffold, chosen by the user: Next.js on Cloudflare, Hono on Workers, oRPC, PostgreSQL with Drizzle on PlanetScale, Alchemy, Better-Auth, pnpm, Biome, Lefthook, Skills addon. No payments and no mobile for now.

Logs: the user asked for evlog with Axiom. The scaffolder refuses both ("Axiom includes evlog"), so the Axiom add-on is used.

## Orchestration

Two Cloudflare Workflows, the user's design:

- `ScanWorkflow` fetches, deduplicates and saves new jobs.
- `ApplicationWorkflow`, one per new job, runs filter, score, prepare, claims check, pauses for the user, apply and proof.

Postgres stays the source of truth. A timeout never approves anything. Queues were dropped because this design replaced them.

## Browser and scraping

- Job lists with no API are scraped through Cloudflare Browser Run (formerly Browser Rendering), using Playwright. Local Playwright is the fallback.
- robots.txt and rate limits are respected. A block or challenge hands over to the user; no bypassing or hiding from bot detection.

## Submission on scored boards (2026-10-31)

Ashby, Greenhouse and Lever score browsers invisibly at submit time. The user chose never to auto-submit on those boards: after approval the application goes straight to the hand-off, with answers and files ready to copy, and the user submits and marks it done. No form is filled automatically there. The form-filling code stays behind this setting, disabled for these boards. Auto-submission covers only boards without such scoring, and none is confirmed yet.

How it is built: a per-board mode (`handoff` or `auto`) fixed in `packages/core/src/apply/modes.ts`, enforced in core at every entry (begin, submit, dry run, the CLI's live dry run), so the UI is not the only gate. Changing a board to `auto` is a code change. The applier's fixture tests enable it only for 127.0.0.1/localhost stand-ins, from test code. Superseded by this: "Real board hosts need `SUBMIT_ALLOWED_HOSTS`" now only limits where an `auto` board's run may go.

## Phase 3 review fixes (Codex, 2026-10-31)

| Decision | Why |
|---|---|
| A submission runs in an allowlist session: navigations, redirects (hop by hop) and every data-sending request must stay on allowed hosts; the page is re-checked before the claim | Only the first URL was checked; an allowed host could redirect to another where the form was filled and posted |
| What a control already holds is read; unapproved defaults are cleared, controls that cannot be emptied become questions; the filled form is re-read before the claim | Preselected gender and marketing boxes were submitted as if approved. Demographic answers are never chosen for the user |
| Claims must cover every fact word of a segment (stemmed, short words and negations included), in their text or their verified quotes; named terms must be in the cited files | 70% word coverage let "and Rust" through. Remaining risk: a checker that paraphrases facts with synonyms fails the check and re-drafts (fails closed) |
| Every interpolated prompt field is escaped; a board's question label is stored as third-party text and is never citable | A label could close the profile block and inject instructions |
| Confirmation requires the board's own transition (exact path or element, text, form gone), after errors and challenges | Any path containing /thanks counted as success |

## Cost and spending cap (2026-10-31)

| Decision | Why |
|---|---|
| Record model, tokens and estimated cost of every call per application; prices in a code table with their source, marked estimated | The user asked to see cost per application; the invoice stays the real figure |
| A model without a price is charged at the highest known rate | Never treat an unknown cost as zero under a cap |
| Monthly cap, on by default, $20, calendar month UTC; checked before each call with a locked worst-case reservation | Real scans tailor every kept job; parallel workflows must not all pass the check at once. The $20 default is the builder's choice, editable in Settings |

- Terms of Use (effective 2026-01-01), https://openai.com/policies/terms-of-use/ (read from the Wayback Machine copy of 2026-10-31; openai.com refused the fetch): "You may not share your account credentials or make your account available to anyone else…" and, under what users may not do, "Automatically or programmatically extract data or Output".
- Sign in with ChatGPT for developers, https://developers.openai.com/siwc: "Sign in with ChatGPT is currently available to selected commercial partners through a limited trial."

Plainly:

- **Personal use is not clearly allowed by either vendor.** Anthropic documents Agent SDK use on a plan login ("draw from your plan's usage limits", "ordinary, individual usage of Claude Code and the Agent SDK"), but its Consumer Terms forbid scripted access except "where we otherwise explicitly permit it", and its compliance page says developers "building products or services … including those using the Agent SDK, should use API key authentication". Whether a personal tool on one's own Mac is "ordinary, individual usage" is not stated. OpenAI documents `codex exec` and the SDK on a ChatGPT login for "trusted private automation" while recommending API keys, and its Terms forbid extracting Output "automatically or programmatically" without naming Codex. Reading either as permission is our inference, not the text.
- **Use in a product for other people is prohibited**: Anthropic forbids offering claude.ai login or routing requests "on behalf of their users"; both forbid making an account available to anyone else.
- So the subscription providers are opt-in, local, single-account, and never the default; the README carries a warning. The user decides whether their use is within the terms.

The user wants better matches. Code rules rejected jobs a careful reader would keep and could
not weigh level, pay or domain, while the weighted fit score let a job needing US citizenship
and a clearance score about 90 on skills. Now no rule rejects a job, and the score itself
